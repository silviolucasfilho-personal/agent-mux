# AGENTS.md — repository guide for coding agents

`agent-mux` is a terminal multiplexer for AI coding harnesses (Claude Code `claude`, Codex CLI `codex`, Google Antigravity `agy`, OpenCode `opencode`, Grok `grok`, Pi `pi`, Muse Code `muse`, Cursor CLI `cursor-agent`; DeepSeek `dsh` not yet supported) with a local SQLite trace store (`~/.agent-mux/traces.db`) and a read-only analysis CLI (`agent-mux trace …`).

## Skills

The only packages agent-mux manages are **skills**: a harness-neutral `SKILL.md` plus optional `skill.toml` and `reference/*.md`, installed into each harness's own skill directory and launched from the Agents sidebar; the Skills view (`S`) is a read-only look at skills and their usage. Details in `docs/skills.md`; code in `src/skill/`.

### Swarm coordinator (`skills/swarm-coordinator`)

The coordinator of a swarm runs this skill (coordinator-first design): it talks the goal over with the operator, submits the plan with `agent_mux_swarm_plan`, shows the table it gets back and asks whether to start, relays the operator's yes with `agent_mux_swarm_launch(operator_said)`, follows the workers with `agent_mux_swarm_wait` (a timeout is a check-in: it reports and asks whether to keep waiting), answers their questions and relays merges and the close with `agent_mux_swarm_action`. `reference/plan.md` holds the splitting rules (the old `swarm-plan` skill). `App::start_swarm_coordinator` installs it and opens the coordinator with a three-line prompt (`prompts.toml` `[swarm] coordinator`, `prompt::coordinator_prompt`) naming the context file `$AGENT_MUX_SWARM_CONTEXT` (`PlannerContext` with `limits`, `tools`, `screen`); invoked by hand in any session, it calls `agent_mux_swarm_start` and that session becomes the coordinator. Visible in the Agents sidebar, `auto_approve = true`, `[agent] mcp = "auto"`.

### Heimdall (`skills/heimdall`)

Heimdall briefs the user on active and recent sessions and evaluates skills and agents (subagents) in depth. Rust computes its facts before launch as a single schema-v2 startup dossier (`$AGENT_MUX_BRIEFING`, `$AGENT_MUX_BRIEFING_SCHEMA=2`, guide: `docs/heimdall-dossier.md`), containing a 24-hour session briefing and 30-day skill/agent metrics. Heimdall answers its startup report directly from the dossier without tool calls; the read-only MCP server (`agent-mux mcp serve`) answers newer or narrower follow-ups, with the `agent-mux trace` CLI as fallback. Its `SKILL.md` holds the tool/command table and playbooks; `reference/sessions.md`, `reference/skills.md` and `reference/agents.md` hold thresholds and report shapes; ad-hoc SQL is in `docs/trace-sql-examples.md`. It is compiled into the binary; a package at `~/.agent-mux/skills/heimdall/` shadows it. `skill.toml` sets `auto_approve = true` and `hydrate = ["dossier"]`.

Invocation per harness (`skill::render::invocation`): `/heimdall` (Claude Code, Antigravity, Grok, Muse, Cursor), `$heimdall` (Codex), `load skill heimdall` (OpenCode), `/skill:heimdall` (Pi). Install with `agent-mux skill install heimdall`; the Agents sidebar launcher installs it automatically before each launch.

## Loops (`src/loops/`, `loops/`)

Loop Engineering: scheduled, bounded, gated runs against one workspace from its row in the Agents list (the `scheduled` rows; `E`/`W` the runs view `src/app/runs_view.rs`, `K` kill switch, `I` the inbox shared with workflows: `src/app/inbox.rs`) and `agent-mux loop …`. A loop chooses its run's model and its verifier sub-agent's model (`model`, `verifier_model` on the entry and the pattern); the verifier's reaches Claude Code only, through the scaffolded agent file's frontmatter (Claude Code, and OpenCode when it is a `provider/model` id). The nine loop skills under `loops/skills`, the verifier under `loops/agents` and the templates under `loops/templates` are agent-mux's own and are installed at project level into the workspace by the scaffolder; they are not Agents-sidebar packages. Facts a run reasons about (budget, breaker, readiness, tokens, files touched) are computed in Rust and handed over in `$AGENT_MUX_LOOP_CONTEXT`; the `PreToolUse` guard enforces the `gate.yaml` denylist, report-only runs and the no-push rule. Claude Code, Codex, OpenCode (agent-mux's plugin carries the guard: `src/opencode_plugin.js`) Muse (`muse exec` with `-c hooks=…`, skills scaffolded to `.agents/skills/` and agents to `.muse/agents/<name>.md` + `--agents <json>`) and Cursor (only once `trace hooks install cursor` has installed the guard; scaffolded to `.cursor/skills/` and `.cursor/agents/`); Antigravity is deferred (spec section 16), and Grok and Pi have no guard. The task library (the loop builder: a scheduled agent's What tab in the agent editor, `o`/`f` on a scheduled row; `src/app/loop_builder.rs`, `src/ui/loop_builder.rs`, model `loops::builder`) edits every pattern, and its cursor is the agent's task; built-in or the user's, and saves it into the library registry by id (`R` restores a built-in). Guide: `docs/loops.md`; design: `docs/superpowers/specs/2026-09-15-loop-engineering-design.md`. Nothing from another vendor is vendored or executed.

## Workflows (`src/workflows/`, `src/app/workflows.rs`, `workflows/`)

A workflow is a TOML document (`[workflow]`, `[args]`, `[schemas]`, `[[steps]]` with kinds `single`, `fanout`, `pipeline`, `route`, `tournament`, `until`, `revise`, plus `verify` votes and transforms) interpreted in Rust; a `revise` step is work, an independent `review` of it (`Role::Review`, its own agent and harness, `harness = "other"` resolved at launch by `App::other_harness`) and the work sent back with the findings up to `max_cycles` times, all in one worktree per step (`LiveWorkflowRun.step_worktrees`, `<run>/worktrees.json`), the review starting only on committed work (`worktree::committed_and_clean`) and its sessions marked `workflow_no_push` for the guard (`guard::no_push_verdict`); a step, its `verify` refuters and its `judge` each choose their own harness, profile, model and effort (`document::Runner`), and step skills are installed for every harness the document names; every session is a headless print-mode run of one of the eight harnesses (command lines and result envelopes in `workflows::harness`) through `spawn_traced_full`, reading `$AGENT_MUX_WORKFLOW_CONTEXT` and answering with a fenced `workflow-result` block. The flow builder (`n`/`e` on a flow, inside the agent editor `src/app/agent_editor.rs`; `src/app/flow_builder.rs`, drawn by `src/ui/flow.rs`) edits a document through `workflows::builder::Draft`, which wraps the document's own TOML table so unknown keys survive; its Steps / What passes / Review screens are the editor's three tabs for a flow, and with the agent form they follow the design canvas "Agent Flow Builder"; a row of the chain is drawn by `ui::step_row` (harness, agent, model; refuters and judge as rows of their own, `FlowBuilderState.sub`). Step skills (`workflows/skills/wf-*`, `hidden = true`, `writes = true` for editors) and the planner (`skills/workflow-author`) are compiled-in skill packages installed user-level per harness. A run is followed on the Run screen (`Mode::Run`, `src/app/run_screen.rs`, `src/ui/run_screen.rs`; `Enter` on a flow's run, or starting one): the run's tree from `workflows::run_view` (`from_live` while it is in memory, `from_stored` after; every step from the start, sessions under a step that has several) where the Agents list is, and the selected row's tabs in the main pane (Board, Live, Timeline, Result, Document; Step, Live, Trace, Changes). Sessions are headless, so Live is a tail of their output decoded by `workflows::live` (Claude, Antigravity and Cursor run with `stream-json`), kept under `<run>/output/` when a session ends; a resumed run records what it replayed in `<run>/replayed.json`. The Workflows sidebar section (`Tab`, `Enter` run, `c` compose, `e` edit, `x` cancel, `W` runs view; plans to review and failed runs also land in the inbox `I`) and `agent-mux workflow ls|show|check|skills|run|plan|runs|status|save` share the runtime. Rows: `workflow_runs`, `workflow_steps`; files under `<runtime>/workflows/<run>/`. Command lines were probed against the installed CLIs (plan, 2026-09-17); when you add a step skill, register it in `skill::builtin_packages`; when you add a document, in `workflows::library::BUILTIN`. Guide: `docs/workflows.md`; design: `docs/superpowers/specs/2026-09-17-workflows-design.md`, and `docs/superpowers/specs/2026-11-13-run-screen-and-flow-editor-ux-design.md` for the Run screen and the flow editor.

## Software factory (`src/factory/`, `workflows/factory.toml`, `workflows/factory-ci.toml`)

One work item (a GitHub issue through `gh`, or text) travels the built-in `factory` flow and ends as a draft pull request. The line is a workflow, so the order of the stations is the interpreter's: `classify` (`route`: `build` / `question` / `clarify`), `research` (a pipeline over the classifier's `research_questions`; none is no session), `analyze`, then `build`, a `revise` step: the `implementer` works and commits in one worktree, the `reviewer` judges the committed diff there with `harness = "other"`, and the work is sent back at most `max_cycles` times. Stations are the agents `classifier`, `researcher`, `analyst`, `implementer` (`agents/builtin/`) plus `reviewer`, running the step skills `workflows/skills/wf-factory-*`. `factory::settle` reads a finished run (status, the journal's `classify` answer, the run's result) and names the item's state; an `approve` with a failing or missing criterion is `unresolved`. `factory::deliver` is the only code that pushes: one ref under `[factory] branch_prefix`, never the default branch (read with `git ls-remote --symref`), never `--force`, hooks off, then `gh pr create --draft` with a body rendered from the stations' answers (`pr_body`); nothing marks a pull request ready or merges it. `factory::brain` is one Markdown file per repository in the library (`<library>/factory/<key>/brain.md`, the key a hash of the normalized `origin`), read by Rust into every station's `args.brain` and written only by the operator: `factory brain add|edit`, or a station's suggested note decided in the inbox (`InboxItem::BrainNote`, `store::pending_brain_notes`, `App::decide_brain_note`; events `brain.note`, `brain.note.added|discarded`); the factory does not use ai-memory. Rows: `work_items` (the partial unique index on `(repo, source, source_ref)` is the intake claim) and `work_item_events`, schema v28 (`factory::store`). CLI: `agent-mux factory run "<text>"|--issue N`, `ls`, `show`, `answer`, `retry` (a fresh run, or only the delivery after a `delivery:` failure), `cancel`, `brain show|path|edit|add`; `poll`; a run is headless in that process (`workflows::cli::headless`), records its pid under `<runtime>/factory/<item>.pid` (`intake::hold`, which `cancel` and the screen's `x` use to stop it) and forks its work from `origin/<default>` (`WorkflowRunRequest.worktree_base`). Phase 2: `factory::intake::poll` (`[factory] intake = "label"`, `factory poll`, started by the TUI every `poll_interval_s` through `App::factory_tick`) turns open issues with the label into unattended items when the login that added the label has `triage` or above (`gh api …/issues/N/events`, `…/collaborators/<login>/permission`), then works the queue one item at a time; `factory::comment` writes on an issue item's issue (one progress comment per run edited in place from the journal, `comment::Progress`, and one outcome comment; `[factory] comments`). The Factory screen (`Mode::Factory`, F1 → Open factory, `ActionId::Factory`; `src/app/factory.rs`, `src/ui/factory.rs`) lists one repository's items by what they wait on, with tabs Item · Line · Thread · Result and the brain as its last row; it starts nothing in-process: `n`/`a`/`r` spawn `agent-mux factory …` (`intake::spawn_cli`, `App.factory_exe` in tests), and `Enter` opens the item's run on the Run screen (`run_screen::Origin::Factory`). Items that need the operator and suggested brain notes are inbox rows (`App::factory_inbox_items`, counted in `App.factory_needs`). Phase 3: `factory::ci` turns red checks on an open pull request the factory delivered into a `ci` item (`Source::Ci`, `source_ref = <pr>@<sha>` so the claim is per failing commit, at most `[factory] ci_fix_max` per pull request; `ci::poll` from `factory poll` with `[factory] ci_fix` or `--ci`; `gh pr checks --json name,bucket,link`, `gh run view --log-failed`), which runs the built-in flow `factory-ci` (`workflows/factory-ci.toml`: analyze, then the same `build` step; no triage, `ci::CLASSIFICATION` stands in) from `origin/<the pull request's branch>` and is delivered by a push to that branch with no new pull request (the item is created with `branch`, `pr_number`, `pr_url` set). `factory::eval` (`agent-mux factory eval`) runs the line with real harnesses in sandboxes (a bare origin and a clone under a temporary folder, a store and runtime of their own, a recording `gh` on `PATH`) and judges five cases from the run's journal, the remote's refs and the `gh` log: `order`, `no-push`, `thin`, `injection`, `unresolved` (a workspace agent named `reviewer` that never passes). Guide: `docs/factory.md`; design: `docs/superpowers/specs/2026-11-15-software-factory-design.md` (its §14 lists where the code differs).

## Projects (`src/project/`, `src/app/project.rs`, `src/ui/project.rs`)

A Project is a repository configured with spec-wave (`.spec-wave.json`, found by walking up; a `role: "code"` repository opens its hub's), read from its GitHub issues and Projects v2 board. Phases 1, 2 and 3 of `docs/superpowers/specs/2026-11-18-issue-based-project-management-design.md` phase 4 in nine parts and phase 5 in four are built (the spec's §19 to §37 say what each left out): reading a Project, the operator's first changes to it, its document steps, the decomposition included, the build of one Story or the fix of one Bug, the fix of a pull request's review comments, the merge, and the tag every step's session carries. `.spec-wave.json` is never written (spec-wave's CLI serializes it byte for byte), and nothing is written to GitHub except by a verb the operator gave. `project::contract` holds every string spec-wave puts on GitHub (the twelve stages of the board's `Etapa` field, tracks and birth stages per type, trigger and state labels, `slugify`, document paths under `docs/features|bugs|rfcs/<slug>/`, artifact branches `spec-wave/<n>-<suffix>`, `Depende de:` lines, closing references), ported from `spec-wave-cli` `packages/spec-wave/src/config.mjs` and its `lib/`; its tests freeze them as literals. `project::config` reads the file (hub or code role, `repositories[]`, the board's ids, `execution.mode`, the older `etapaFieldId`/`stageOptions` pair). `project::github` is every `gh` call (through `factory::deliver::Tools`, so a test names a stand-in): one GraphQL query per 50 issues returns labels, milestone, parent, sub-issues, `blockedBy`, closing pull requests and the board's field values, sent again without the Projects v2 part when gh's token lacks the `project` scope (probed against a real hub on 2026-11-18); the reads run side by side. `project::snapshot::build` is pure over what was read: a read that failed never becomes a fact (a document whose listing failed is `DocState::Unknown`, never `Missing`), and a code repository's pull requests are linked by the hub issue they name, since GitHub's link does not cross repositories. `project::stage` is spec-wave's `planStageMove` (a stage only advances; an item at a stage outside the canonical order is never moved) plus a derived stage for an issue that is not on the board; `project::next` is the port of `nextStep` with its block codes (`describe` adds a line for Stories, Tasks and the stages past Ready); `project::order` is its `orderStories` with the `order` command's warnings. `project::write` is every mutation (`gh api`, `gh issue edit|comment`, the GraphQL `addProjectV2ItemById`, `updateProjectV2ItemFieldValue`, `addSubIssue`; `write::Board::resolve` takes the board's ids from the file, from the hub's checkout beside a code repository, or from the board itself), and `project::ops` is the verbs with spec-wave's rules: `new_item` (birth stage per type, a Story or Task only under a parent), `move_item` (only forward, confirmed by reading the board again), `repair_stage` (may go back; needs `--yes` and a reason, leaves a note on the issue), `task`, `story_review`, `triage` (a P2/P3 Bug needs `spec-wave:bug-approved`) and `auto_moves`/`apply_moves` (the board moves the pull requests justify, made only on the operator's word). Document steps: `project::run` plans a step (`Ctx::plan`, over `next::next_step`; a forced `--step` still stops at `needs-human`, `pr-pending` and a trigger label), and finishes it (`finish_generate`, `finish_critique`, `stop_for_human`, `validate`); the session in between is one of the built-in flows `project-spec|plan|bug|critique|decompose|decompose-rfc` (`workflows/project-*.toml`, one read-only step `work`, skills `wf-project-*` ported from spec-wave's `model-prompt*.md` in Portuguese, agents `spec-writer`, `tech-lead`, `critic`), run headless by `project::cli::run_flow`. **The session writes no file**: the document travels in its result (`{document}`) and `project::deliver::publish` commits it in a temporary detached worktree forked from `origin/<default>`, pushes `HEAD` to `spec-wave/<n>-<suffix>` under the factory's push rules (one ref, never the default branch, no force, hooks off) and opens a pull request that is not a draft; the operator's checkout is never touched. The decomposition is two steps with a file a person edits in between: `project::decomposition` is `decomposition.md` (`render`, `parse`, the port of spec-wave's `decomposition-doc.mjs`: `## Story N`, `### Task N.M`, `**Depende de:**`, `**Repos:**`, `**Issue:**`; reversible, position decides and not the number written, a forward dependency is an error) and `dependency-map.json` (byte for byte spec-wave's, frozen by a test); the draft's session answers `{stories}` or `{tasks}` (flows `project-decompose`, `project-decompose-rfc`, skill `wf-project-decompose`) and Rust renders the file; `project::apply` (`Ctx::apply_plan`, `Ctx::apply`) creates the Story and Task issues from the merged draft with no model, only on `--apply`, refusing a second apply (the `decomposed` label, the draft's `applied=`, existing children) and journaling each created issue by its position under the scratch folder so an apply that stopped resumes without a duplicate. Development: `project::build` is the `build` step of a Story and the `fix` step of a Bug (spec §23). `build::decision` (pure) says whether `project run` on an item is a development step and what stops it (`not-ready`, `pr-pending`, `dependency-pending`: a dependency counts once it is merged, since the build forks from the default branch; `with-story` for a Task, `by-story` for a Feature, which names its next Story); `Ctx::build_plan` reads everything and writes nothing: the one repository of the item's `repo:<slug>` label (`target_repo`, `repo_dir`: spec-wave's `resolveWorkspaceLayout`, the override in `.spec-wave/workspace.json`, the folder beside the hub, the managed clone; no label is the hub; the folder's `origin` must be that repository), the branch `story/<n>-<slug>` or `fix/<n>-<slug>` (refused when it is already on the remote), and the context, the port of spec-wave's `buildContext` and `buildBugContext` in Portuguese with the delivery left to agent-mux (`story_context`, `bug_context`; criteria from the Story's "Critérios de aceite" bullets and one per Task, `BUG_CRITERIA` for a Bug). The session is the flow `project-story` or `project-bug-fix` (one `revise` step `build`: agent `implementer` with skill `wf-project-build` in a worktree forked from `origin/<default>`, agent `reviewer` with `wf-project-review` and `harness = "other"`, `max_cycles = 2`), run by `cli::run_flow_in` in the code repository. `Ctx::build_start` and `Ops::build_board` move the board as spec-wave's `planBoardMoves` does (best effort: a failed move is a line); `Ctx::build_finish` delivers only what `factory::settle` would (an approval with every criterion passing): it checks the commits for spec-wave's trailers (`build::trailers`, `parse_trailers`, `missing_trailers`, the port of `commit-trailers.mjs`; one empty commit adds them when missing), pushes with `factory::deliver::push`, opens the draft pull request with `Closes <hub>#<n>` (`Fixes` for a Bug; `build::pr_body`), moves the Tasks to Done and the item to Code Review, and comments on the issue. No session pushes or touches GitHub, and a build merges nothing. Review and merge (spec §24): `project::fix_pr` is the `fix-pr` step (`project run <n> --step fix-pr`): `open_comments` (pure) takes the review threads that are not resolved and carry no reply with `fix_pr::MARKER`, plus a review body submitted after the branch's last commit, read with one GraphQL query; the flow `project-fix-pr` is the same `revise` step forked from `origin/<the pull request's branch>` (skill `wf-project-build` with `kind = "fix-pr"`, one commit per comment, answering `fixes` and `declined` rows); `Ctx::fix_finish` delivers only an approval with every criterion passing: a push to that branch, a reply under each thread with its commit (only one that is on the branch) and a summary on the pull request. `project::merge` is the port of spec-wave's `merge` and the only code that merges, on `--yes`: `scope` (a Feature's Stories by `order::order_nodes`, or one Story or Bug), `plan` (pure, spec-wave's `planMerge`: a draft or two open pull requests in one repository block everything), `execute` (each pull request read again, `gh pr edit --base`, `gh pr merge --merge`, never `--delete-branch` or a squash, `Ops::merged_board` to QA, the branches deleted at the end; a refusal stops the queue and a second run resumes). Every session a step starts carries `launches.metadata.project` (`project::ProjectLaunch`: hub, item, type, feature, step, attempt, role, run; set on the headless app as `App.project_launch` by `cli::run_flow_in` and written by `spawn_traced_full`), and `tracing::project_report` reads an item, with what is under it in the cache, as one trace (`agent-mux trace project <n> [--tree|--log|--json]`). The same report adds things up (spec §31): `hub_launches`, `item_totals` (an item's own sessions and, rolled up every ancestor of the snapshot, those under it) and `card_line` for the `Sessions:` line of a card (`ProjectView.totals`, `project show`); `observability_lines` for the Observability screen (`Screen::Observability`, a screen with no rows: `ProjectView.activity`, the last 30 days and ever); `timeline_lines` for `trace project <n> --timeline`; and Heimdall's dossier has a `projects` section (`dossier::ProjectCard`, `project_card`: the workspace's own Project, from the launches of the window and `project_dispatches`). That trace is shown in four more places (spec §25): the item screen's sixth tab, Trace (`app::project::ItemTrace`, read on the spot by `App::project_load_trace` when the tab opens; `project_report::runs` groups the sessions by workflow run, and `Enter` opens a run on the Run screen with `run_screen::Origin::Project`, `App.project_return`); the History badge `#<n> <step>` (`project_report::session_steps`, `App.history_steps`, `HistoryState.steps`, `p` on the History screen for the sessions of steps only); the MCP tool `agent_mux_get_project_item` (`mcp::server::project_item_result`); and Langfuse, one session per work item (`map::MapCtx::projects`: `session.id = <hub>#<n>`, tags `project`, `project:<step>`, `milestone:<m>`; `map::project_summary` is the summary trace, sent by `project::cli` after a build, a fix or a fix-pr through `langfuse::send_project_summary`, and by `agent-mux langfuse export-project <n>`). Stacks (spec §26): `project::stack` is a Feature built as a stack (`project run <feature>`, `Planned::Stack`): `plan` (pure, the port of spec-wave's `planFeatureImplementation`: pending Stories in dependency order, the ones in code review left alone, a cycle or a pending Story with no Task an error), `base_for` (a Story forks from, and its pull request is based on, the branch of the nearest Story before it with an open pull request in the same repository; applied to a Story run alone too), `under` with `build::check_stack` (a dependency's open branch must be an ancestor of the base, checked with git after the fetch), and `mark_ready` (`gh pr ready`, the one place a draft is marked ready: when every open Story of the Feature is in code review, over the open pull requests that name them, read by `stack::collect`; `--keep-drafts` skips it). `cli::build_all` runs a planned build to its end and keeps a copy of the snapshot in step with what was delivered, for the next Story's base. `snapshot::build` links the hub's stacked pull requests by their closing lines, since GitHub links only one based on the default branch. A Story with several `repo:<slug>` labels is built one repository at a time (`build::targets`, `build::Part`, `part_note`; the board moves after the last, `Part::last`), and a Task is built on its own (`BuildKind::Task`, `task_context`, branch `task/<n>-<slug>`, ending Done). Proposals and the chat (spec §27): `project::assist` is `project estimate|refine <n>`: a read-only flow (`project-estimate` with skill `wf-project-estimate`, `project-refine` with `wf-project-refine`) answers, Rust checks the answer (`fit` to the options of the board's `Story Points` field; `check_refined`: the `Depende de:` lines, HTML comments and checked boxes are kept) and saves a `Proposal` under the scratch folder; **nothing is written without `--yes`**, which writes the waiting proposal with no second session (`Ctx::apply_proposal`: `Ops::set_story_points`, or `write::set_body` after checking the description's hash against GitHub). On the screens `E` and `W` ask for a proposal or ask to write the waiting one (`ProjectView.proposals`, shown on the card), and `c` is `App::project_chat`: an interactive session in the hub's folder whose opening message invokes the visible built-in skill `skills/project` (`/project`, `app::project::chat_opening`), tagged `metadata.project` with `role = "chat"` through `App.launch_project`. `a` is `App::project_agent`: the same session as one of the operator's personas (`ProjectView.agents`, the launch plan of `App::session_agent`, `agent_opening`, `role = "agent"`). `project::insights` is `project insights [<n>] [--scope progress|tech|daily|brainstorm]` (flow `project-insights`, skill `wf-project-insights`): a read-only session over `insights::digest` (pure: open items per stage, milestones, one line per open item with its next step), whose answer is kept under the scratch folder and opened by `I`. The MCP server answers `agent_mux_project_list|item|next` from the cache, never from GitHub. The fleet (spec §28): `project::fleet` is the dispatches (`project_dispatches`, schema v31; an item with no row is in Backlog), the pure dispatcher `next_actions` over `cards` (slots, Bugs first, a dead run is lost, an open pull request in code review is Review) and `settle`/`block`; `project::lease` is `spec-wave-agent`'s lease on git refs, ported rule by rule (non-forced push to acquire, `--force-with-lease` on the sha seen to renew or steal after `TTL_SECS`, `generation`; refs under `lease::DEFAULT_PREFIX` on the hub's remote, kept in a repository of its own under the runtime folder), so the daemon and other machines see each other's claims. The runner is `cli::fleet_run` (`agent-mux project fleet run [--once]`, one per hub and machine by pid file): each run is `agent-mux project run <n>` as a child process (`AGENT_MUX_PROJECT_EXE` names a stand-in in tests) under a lease it renews every `HEARTBEAT_SECS`; a lost lease stops the child and blocks the card. `project dispatch|cancel <n>`, `project fleet status`; on the Development screen `app::project::kanban_rows` puts the fleet's WIP, Blocked and Review over the backlog, and `d`/`x`/`b` start `project fleet run --once --dispatch <n>` or `project cancel <n>` after a confirmation. Its settings are `[project.fleet]` (`config::resolve_fleet`: `max_runs`, `max_failures`, `delivery`, `label`, `queue_label`, `request`; a flag of `fleet run` wins). ## Agents (`src/agents/`, `agents/templates/`)

A workflow agent is the *who* of a session: a TOML file (`name`, `description`, `instructions`, canonical `tools` = `read|edit|shell|web|mcp:<server>`, `model`, `effort`, `[backends.<harness>]`) in `<workspace>/.agent-mux/agents/` or `~/.agent-mux/agents/`, else one of the built-ins in `agents/builtin/` (`agents::BUILTIN`: reviewer, skeptic, planner, doc-writer, judge), which a library file of the same name replaces. A step, a `verify` block or a `judge` names one with `agent = "…"` (refuters and judges do not inherit the step's). `agents::launch::plan` turns it into command-line changes per harness (Claude `--agents`/`--agent`, Codex `-c developer_instructions` and `-s read-only`, agy `--agent` plus a managed file under `~/.gemini/config/agents/agent-mux-<name>/`, OpenCode an inline agent in `OPENCODE_CONFIG_CONTENT`, Grok `--rules`, Pi `--append-system-prompt` and `--tools`, Muse `--disable-write`/`--disable-shell`, Cursor a `preamble` ahead of the first message and `--mode ask` without `edit`); `agents::fit::check` runs in `workflow check` and at run start; the journal records `agent`/`agent_hash` and a resume reruns from the first step whose agent changed. The planner lists agents in its context and may define new ones in `agent-toml` blocks (`workflows::planner::check_agents`, `save_agents`). The same file can be a task agent: `[task]` names one of `pattern` (a loop pattern), `skill` or `prompt`; without `[schedule]` it runs on demand (`Enter` on its row: `App::open_agent_session`, `session_agent`), with it on a schedule (a skill or prompt task defines its own pattern, `schedule::task_pattern`), and `[limits]` sets budgets; `agents::schedule` overlays library agent files on `loops.json` (which keeps the run state; `LoopEntry.agent` links them), the agent editor writes them, and `agent migrate` writes one per older loop. Load the registry through `agents::schedule::load_registry`, not `registry::load`, so the files apply. CLI: `agent-mux agent ls|show|new|check|templates|import|migrate` (`import` is the loop-agent importer). Guide: `docs/agents.md`. Do not confuse with loop agents (`loops/agents/*.md`, Claude-shaped files the loop scaffolder installs).

## Library (`src/app/library.rs`, `src/ui/library.rs`)

The Library screen (`Mode::Library`; `o` in the Agents list, or F1 → Open library, `ActionId::Library`) holds every definition and the sessions they launched, with the Swarm screen's layout and conventions:
- **Tree** (`ui::library::draw_tree`, at `ui::SIDEBAR_WIDTH`): rows `library::Row`: a section heading (flows / skills / personas / scheduled), its items (glyph, name, and on the right `●n` going or the `n/8` coverage), and under an item what it launched: `Row::Session` (by session id) and `Row::Run` (a flow's run in flight). Scheduled rows are `loop_registry` loops with their `r`/`p`/`e`/`d` verbs, since legacy loops are not catalog personas. It is drawn as the Agents and Swarm trees are (focus border and `• Keyboard focus` title, `>` marker, reversed cursor row); `LibraryState.anchor` keeps the cursor on its row when a session starts or ends elsewhere.
- **Sessions live here, not in the Agents list:** a session with no group that runs a Library persona or a listed skill belongs to that item (`App::library_item_of`) and `App::session_listed` leaves it out of the Agents sidebar, as it does a swarm's, unless `[agents] show_library = true`; the sidebar says how many are going. `App::reveal_session` (used by `attach_to_session`, the New session dialog's launch and Return to session) shows such a session on its Library row with its terminal focused (`open_library_on_session`).
- **Main pane** (`draw_pane`): the selected row. A session is drawn through the Agents screen's pane (`ui::draw_session_pane`) and `Enter` types into it (`pane_focused` → `Action::ForwardBytes`, to `App.selected`, which `App::library_sync` keeps on the pane's session; the Focus chord returns to the tree). An item is its card in tabs (flow Overview · Harnesses · Runs · Document; skill Details · Harnesses · Executions; persona Card · Harnesses · Runs; scheduled Card · Runs); Runs / Executions are read when the tab opens (`library_history`: the runs view's items, `query::skill_launches`). A heading shows the section's blocked-harness audit.
- **Launch:** one harness picker for every item (`Enter`/`r`): every harness with a Ready / Degraded / Blocked / Not installed verdict and its reason, Blocked rows shown but not pickable. The verdicts come from one coverage reader (`library::{skill_verdict, persona_verdict, flow_verdict}`, over `skill::install::status`, `agents::launch::tool_notes`, `agents::fit::check_on` and `session::command_available`), read once per item while the screen is open (`library_verdicts_in`, `Ctrl+R` reloads), so the tree, the tab and the picker never disagree. Launches reuse the old dialogs (`App::open_skill_launcher_on`, `App::open_agent_session_on`, `App::open_workflow_run_on`).
- **Coming back:** a dialog or an editor the Library opens (`e` the flow builder, agent editor or `$EDITOR` for a skill; `n` the new-item paths; `x` the kill confirmation) returns to the Library when it closes: `handle_library_key` keeps the state in `App.library_return` and `App::library_resume` (after a key and on the tick) restores it when the mode is `Main` again.
- **Keys:** the local verbs go through the action registry like every screen (`command_availability` knows the Library's row), so add a verb there, not only in `library_key`. `/` filters (text entry: letters are literal), `i` goes to an item's session or opens a session's run screen, `←`/`→` move between a row and its parent or child, clicks and the wheel go through `App::library_mouse` (areas from the last frame, `LibraryState.drawn`).

Every harness runs every kind now: personas are applied on Grok (`--rules`, probed live 2026-11-14) and Pi (`--append-system-prompt` + `--tools`), and workflow steps run on Grok (`--single --output-format json`) and Pi (`--print --mode json`) with envelopes parsed in `workflows::harness`; the `wf-*` step skills declare all eight harnesses. Swarm workers still exclude Grok and Pi (`swarm_harnesses`, their MCP reach), and the Skills view (`S`) keeps per-harness install state and executions. Spec: `docs/superpowers/specs/2026-11-14-library-screen-flows-skills-personas-design.md` (§11 is the revision to the Swarm screen's conventions).

Since schema v21 agent-mux runs a swarm itself (the dispatcher), and since v24 the coordinator steers it from its chat:
1. The coordinator, an interactive session (`App::start_swarm_coordinator`, `bus::swarm::prompt::coordinator_prompt`, skill `skills/swarm-coordinator`, `$AGENT_MUX_SWARM_CONTEXT`, prompt `[swarm] coordinator`; schema v22 `swarm_coordinators`), talks the goal over with the operator and submits the plan with `agent_mux_swarm_plan` (CLI `swarm submit-plan`).
2. `record::submit_plan` checks it (`bus::swarm::plan`) and answers errors to the coordinator, or puts it on the board (`swarms`, `swarm_tasks`) and answers the plan as a table. The coordinator then answers workers' questions (`to = "coordinator"`, `record::coordinator_address`) and is told task events in batches (`App::tell_coordinator_events`).
3. The operator confirms in the coordinator's chat, and the coordinator relays it (`agent_mux_swarm_launch(operator_said)`; from a shell `agent-mux swarm approve`). The screen never approves a plan.
4. The pure dispatcher `bus::swarm::engine::next_actions`, run by `app::swarm_engine` on every tick:
   - starts each worker with its whole task as the opening prompt (`bus::swarm::prompt`, `SpawnWorker.opening_prompt`)
   - nudges a worker idle on its task once
   - advances the swarm

5. A worker's `task_split` or `delegate` becomes a proposal on its board (`record::swarm_of_worker`, `record::propose`).
6. The swarm's optional check command runs (`bus::swarm::check`, `Action::RunCheck`) before it reads `finished`.
7. The launch form ticks the workers' pool (`record::worker_pool`, `--worker-harness agy,codex`); the coordinator assigns each task one of them, `plan::check` refuses others, and tasks that name none run on its first (`record::worker_harness`; the coordinator defaults to Claude). A start that fails keeps the form open with the reason (`SwarmBoard::launch_failed`). The task form, and `r`'s retry form, change a task's harness, agent and isolation. agy with a writing agent is refused by `plan::check`, by the task and retry forms (a retry starts on Claude) and by `SpawnWorker`: agy 1.4.12 runs custom agents read-only.

8. Since schema v23 a workspace may run several swarms: verbs name theirs by id (`App::swarm_action_on`, `record::resolve_swarm`, `record::swarm_of_task`, `--swarm`), and `plan_blocks` gates a task by its own swarm.

9. Since schema v24 (coordinator-first design, `docs/superpowers/specs/2026-11-05-swarm-coordinator-first-design.md`) the coordinator launches and agent-mux supervises: the engine **offers** a ready task (`engine::Action::Offer`, `swarm_dispatch`), the coordinator starts it with `agent_mux_swarm_launch` (`record::launch`, quoting the operator's yes in `operator_said`; a `swarm_decisions` row with `by = chat|tui|cli`), and the dispatcher starts it itself after `DISPATCH_GRACE_NS`. `agent_mux_swarm_start|wait|board|action` (`agent_mux_swarm_action` includes `delete`; `src/mcp/swarm_tools.rs`, `bus::swarm::view`) and `agent-mux swarm launch|wait|events|cancel|delete` share the rows; `swarm_events` is the log (`bus::store::update_task` adds `task.<status>`, `send_message` adds `message`/`question.*`); every launch carries `launches.metadata.swarm_*` (`bus::swarm::SwarmLaunch`, `from_metadata`). Gate modes: `chat` (default) and `off`; the screen never approves a plan.
10. **One swarm, one trace** (spec §7): `tracing::swarm_report` reads a swarm as one tree (`report`, `tree_lines`, `timeline`, `log_lines`, `launch_trace_lines`, `swarms_since`); `agent-mux trace swarm <id> [--tree|--timeline|--log|--json]` and `agent_mux_get_swarm` answer from it, Heimdall's dossier gains a `swarms` section (`SwarmCard`), and Langfuse gets one session per swarm (`map::MapCtx::swarms`, `session.id = <swarm id>`, tags `swarm`, `swarm:<role>`) plus a summary trace on close (`map::swarm_summary`, `App::export_swarm_trace`, `agent-mux langfuse export-swarm <id>`).
11. **Reviews** (schema v25, `bus::swarm::review`): every new swarm reviews each finished task before the merge unless the operator turns it off (launch form **Reviews**, `--review auto|off|<harness>`, `agent_mux_swarm_start(review)`, the plan's `review {enabled, harness}` and a task's `review = false`; tables `swarm_review_settings`, `swarm_task_reviews`; no settings row means off). The engine's `Action::AddReview` (`engine::needs_review`, which also keeps the swarm from settling) makes `record::add_review` put a `<key>-review` task on the board (`SwarmTaskExt.review_of`/`review_task`), on `review::harness_for` (a pool harness other than the worker's, agy last and without the agent) as the `reviewer` agent, shared; it is offered and spawned like a task, but in the reviewed task's worktree with `review::prompt` (read-only, verdict on the result's first line: `APPROVE` or `CHANGES` + findings). `review::state` reads the verdict for the board badge, the Task tab, `BoardView.reviews` and the merge warning (`record::unreviewed_warning`, `Confirm::Merge.warning`); `SwarmVerb::Review` adds a new review after a fix round. The coordinator skill keeps the step in every plan (`plan_table`'s review column and `Review:` line).
12. **Recovery and the merge gate** (schema v26; `bus::swarm::recovery`, `bus::swarm::gate`; tables `swarm_task_recovery`, `swarm_merge_gates`, `swarm_merge_settings`).
    - **Recovery:** the engine retries a task once on its own (`MAX_AUTO_RETRIES`). It emits `MarkLost`/`ClearLost` when a task's worker is gone or back (workers are looked up by launch id, or by the `session-<n>` placeholder of an untraced one: `app::swarm_engine::bus_launch_id`), and `Recover` (`engine::recovery_due`) for a failure younger than `FAILED_FRESH_NS`, or a lost worker past `LOST_GRACE_NS`. That also keeps the swarm from settling. `recovery::retry` reopens the task, asks for it as the dispatcher, and moves a failure to another pool harness (`retry_harness`; a lost task keeps its own). The reason goes into `worker_prompt`. A lost task whose retry is spent gets `GiveUp` (failed). A worker the operator stopped is held (`App::hold_swarm_worker`, `recovery::hold`) and never retried automatically. The operator's `retry` resets the row. The coordinator hears `task.retried`, and the blocked tasks via `recovery::gave_up_note`.
    - **Merge gate:** a per-swarm setting, off by default (`gate::MergeGateSettings`: `on` = the swarm's `check_cmd`, or a command of its own; launch form **Merge gate**, `--merge-gate`, `agent_mux_swarm_start(merge_gate)`; `command_for` feeds `engine::Input.merge_check`; on a running swarm `SwarmVerb::MergeGate` changes it, its value in the verb's notes, through `record::apply_with` → `change_merge_gate`, which puts queued merges back to waiting when it turns off; `M` on the Swarm screen, `swarm merge-gate`). With it on, `merge` queues the branch (`record::queue_merge`). `engine::gate_due` runs one gate per swarm at a time (`Action::RunGate`), oldest first; an abandoned run counts as queued. On a thread, `gate::test_branch` merges the workspace `HEAD` into the branch in its worktree (else a temporary `.loop-worktrees/merge-gate-*`) and runs the check. `gate::land` then merges into the workspace only on a pass with `HEAD` unmoved (moved: queued again; failed: the branch keeps waiting). `SwarmVerb::ForceMerge` (`force-merge`) merges past it.

The coordinator-era tables `swarm_state` and `swarm_plans` (v17, v19) are left in the schema, unused.

## Working in this repository

- Trace store schema: `src/tracing/store/schema.rs` (migrations through `PRAGMA user_version`, v31 today). Never write to a user's store from analysis code. - Harness command lines are checked against the installed CLIs (`--help`), not documentation; record what you probed in the module docs.
