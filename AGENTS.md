# AGENTS.md — repository guide for coding agents

`agent-mux` is a terminal multiplexer for AI coding harnesses (Claude Code `claude`, Codex CLI `codex`, Google Antigravity `agy`) with a local SQLite trace store (`~/.agent-mux/traces.db`) and a read-only analysis CLI (`agent-mux trace …`).

## Skills

The only packages agent-mux manages are **skills**: a harness-neutral `SKILL.md` plus optional `skill.toml` and `reference/*.md`, installed into each harness's own skill directory and launched from the Agents sidebar; the Skills view (`S`) is a read-only look at skills and their usage. Details in `docs/skills.md`; code in `src/skill/`.

### Heimdall (`skills/heimdall`)

Heimdall briefs the user on active and recent sessions and evaluates skills and agents (subagents) in depth. Rust computes its facts before launch as a single schema-v2 startup dossier (`$AGENT_MUX_BRIEFING`, `$AGENT_MUX_BRIEFING_SCHEMA=2`, guide: `docs/heimdall-dossier.md`), containing a 24-hour session briefing and 30-day skill/agent metrics. Heimdall answers its startup report directly from the dossier without tool calls; the read-only MCP server (`agent-mux mcp serve`) answers newer or narrower follow-ups, with the `agent-mux trace` CLI as fallback. Its `SKILL.md` holds the tool/command table and playbooks; `reference/sessions.md`, `reference/skills.md` and `reference/agents.md` hold thresholds and report shapes; ad-hoc SQL is in `docs/trace-sql-examples.md`. It is compiled into the binary; a package at `~/.agent-mux/skills/heimdall/` shadows it. `skill.toml` sets `auto_approve = true` and `hydrate = ["dossier"]`.

Invocation per harness: `/heimdall` (Claude Code, Antigravity), `$heimdall` (Codex). Install with `agent-mux skill install heimdall`; the Agents sidebar launcher installs it automatically before each launch.

## Loops (`src/loops/`, `loops/`)

Loop Engineering: scheduled, bounded, gated runs against one workspace from its row in the Agents list (the `scheduled` rows; `E`/`W` the runs view `src/app/runs_view.rs`, `K` kill switch, `I` the inbox shared with workflows: `src/app/inbox.rs`) and `agent-mux loop …`. A loop chooses its run's model and its verifier sub-agent's model (`model`, `verifier_model` on the entry and the pattern); the verifier's reaches Claude Code only, through the scaffolded agent file's frontmatter. The nine loop skills under `loops/skills`, the verifier under `loops/agents` and the templates under `loops/templates` are agent-mux's own and are installed at project level into the workspace by the scaffolder; they are not Agents-sidebar packages. Facts a run reasons about (budget, breaker, readiness, tokens, files touched) are computed in Rust and handed over in `$AGENT_MUX_LOOP_CONTEXT`; the `PreToolUse` guard enforces the `gate.yaml` denylist, report-only runs and the no-push rule. Claude Code and Codex only; Antigravity is deferred (spec section 16). The task library (the loop builder: a scheduled agent's What tab in the agent editor, `o`/`f` on a scheduled row; `src/app/loop_builder.rs`, `src/ui/loop_builder.rs`, model `loops::builder`) edits every pattern, and its cursor is the agent's task; built-in or the user's, and saves it into the library registry by id (`R` restores a built-in). Guide: `docs/loops.md`; design: `docs/superpowers/specs/2026-09-15-loop-engineering-design.md`. Nothing from another vendor is vendored or executed.

## Workflows (`src/workflows/`, `src/app/workflows.rs`, `workflows/`)

A workflow is a TOML document (`[workflow]`, `[args]`, `[schemas]`, `[[steps]]` with kinds `single`, `fanout`, `pipeline`, `route`, `tournament`, `until`, plus `verify` votes and transforms) interpreted in Rust; a step, its `verify` refuters and its `judge` each choose their own harness, profile, model and effort (`document::Runner`), and step skills are installed for every harness the document names; every session is a headless print-mode run of Claude Code, Codex or Antigravity through `spawn_traced_full`, reading `$AGENT_MUX_WORKFLOW_CONTEXT` and answering with a fenced `workflow-result` block. The flow builder (`n`/`e` on a flow, inside the agent editor `src/app/agent_editor.rs`; `src/app/flow_builder.rs`, drawn by `src/ui/flow.rs`) edits a document through `workflows::builder::Draft`, which wraps the document's own TOML table so unknown keys survive; its Steps / What passes / Review screens and the agent form follow the design canvas "Agent Flow Builder". Step skills (`workflows/skills/wf-*`, `hidden = true`, `writes = true` for editors) and the planner (`skills/workflow-author`) are compiled-in skill packages installed user-level per harness. The Workflows sidebar section (`Tab`, `Enter` run, `c` compose, `e` edit, `x` cancel, `W` runs view; plans to review and failed runs also land in the inbox `I`) and `agent-mux workflow ls|show|check|skills|run|plan|runs|status|save` share the runtime. Rows: `workflow_runs`, `workflow_steps`; files under `<runtime>/workflows/<run>/`. Command lines were probed against the installed CLIs (plan, 2026-09-17); when you add a step skill, register it in `skill::builtin_packages`; when you add a document, in `workflows::library::BUILTIN`. Guide: `docs/workflows.md`; design: `docs/superpowers/specs/2026-09-17-workflows-design.md`.

## Agents (`src/agents/`, `agents/templates/`)

A workflow agent is the *who* of a session: a TOML file (`name`, `description`, `instructions`, canonical `tools` = `read|edit|shell|web|mcp:<server>`, `model`, `effort`, `[backends.<harness>]`) in `<workspace>/.agent-mux/agents/` or `~/.agent-mux/agents/`, else one of the built-ins in `agents/builtin/` (`agents::BUILTIN`: reviewer, skeptic, planner, doc-writer, judge), which a library file of the same name replaces. A step, a `verify` block or a `judge` names one with `agent = "…"` (refuters and judges do not inherit the step's). `agents::launch::plan` turns it into command-line changes per harness (Claude `--agents`/`--agent`, Codex `-c developer_instructions` and `-s read-only`, agy `--agent` plus a managed file under `~/.gemini/config/agents/agent-mux-<name>/`); `agents::fit::check` runs in `workflow check` and at run start; the journal records `agent`/`agent_hash` and a resume reruns from the first step whose agent changed. The planner lists agents in its context and may define new ones in `agent-toml` blocks (`workflows::planner::check_agents`, `save_agents`). The same file can be a task agent: `[task]` names one of `pattern` (a loop pattern), `skill` or `prompt`; without `[schedule]` it runs on demand (`Enter` on its row: `App::open_agent_session`, `session_agent`), with it on a schedule (a skill or prompt task defines its own pattern, `schedule::task_pattern`), and `[limits]` sets budgets; `agents::schedule` overlays library agent files on `loops.json` (which keeps the run state; `LoopEntry.agent` links them), the agent editor writes them, and `agent migrate` writes one per older loop. Load the registry through `agents::schedule::load_registry`, not `registry::load`, so the files apply. CLI: `agent-mux agent ls|show|new|check|templates|import|migrate` (`import` is the loop-agent importer). Guide: `docs/agents.md`. Do not confuse with loop agents (`loops/agents/*.md`, Claude-shaped files the loop scaffolder installs).

## Configuration library (`src/assets.rs`, `src/prompts.rs`, `src/config_cli.rs`, `src/app/config_view.rs`)

Every compiled-in text (the prompts in `src/prompts.toml`, the Heimdall files, `loops/registry.toml`, the loop skills, the verifier, the templates, the workflows, the built-in agents in `agents/builtin/`) is shadowed file by file from `~/.agent-mux/` (`$AGENT_MUX_LIBRARY_DIR`); `prompts.toml` and `registry.toml` merge by key and by pattern id. The Configuration view (`C`) and `agent-mux config ls|show|path|edit|reset|new|check|push` list, edit (external editor: `editor` in profiles.toml, `$VISUAL`, `$EDITOR`, `vi`), reset, create and push items. Consumers read the effective text: `loops::patterns::all()` (cached, `reload()`), `loops::scaffold` (`scaffold_with_library`), the loop launch prompt (`prompts::render_loop_run`, a pattern's `prompt` first) and the hydration hint. When you add a compiled-in asset, register it in `Catalog::load` so it is editable; nothing pre-defined is read-only (built-in agents, loop patterns and workflows are also editable in the builders). Guide: `docs/configuration.md`; design: `docs/superpowers/specs/2026-09-17-configuration-library-design.md`.

## Agents list (`src/app/agents_list.rs`)

The sidebar is Agents + History (agent-first spec, 2026-09-26). `App::agent_lines` builds the rows (harnesses, scheduled loops, flows, skills, personas, sessions nested under their owner); moving the cursor selects the same thing the old sections selected (`sidebar_section` + its index), so section-based actions keep working. Rows with no older home (a harness, a persona, an orphan run) live in `App::agent_focus`. `n` opens `app::new_agent`; "describe it" runs the planner, which may answer with one agent (`planner::extract_agent_draft`, reviewed from the runs view with `App::open_agent_draft`) instead of a flow. A scheduled agent, a flow and a persona are edited in one agent editor (`src/app/agent_editor.rs`, `src/ui/agent_editor.rs`, tabs Who · What · When · Limits · Review); every run is listed in the runs view (`src/app/runs_view.rs`, `src/ui/runs.rs`). `f` on a session continues it in a new one (`src/handoff.rs`, `App::session_handoff`): the same Claude Code or Codex forks the conversation (`harness::Resume::Fork`), any other harness reads its whole transcript from a handed-over Markdown file. Tests reach a kind of row with `App::select_first_row_of(section)`.

## Memory (`src/memory/`, `src/app/memory_view.rs`, `src/ui/memory.rs`)

agent-mux keeps no memory of its own: it installs and wires ai-memory (github.com/akitaonrails/ai-memory), whose server (`127.0.0.1:49374`, launchd agent `com.github.akitaonrails.ai-memory`) captures sessions through the hooks it installs per harness and answers over MCP. `memory::State::detect` reads the binary (`$AI_MEMORY_BIN`, `PATH`, `~/Applications/ai-memory`, the menu bar app), the server port, the launchd plist, and each harness's MCP entry and hooks from its files; `memory::install::plan` turns what is missing into `Step`s (download the macOS release with its `.sha256`, `ai-memory init`, the launchd agent, `install-mcp --client` and `install-hooks --agent` per harness), shown before they run; `plan_uninstall` runs `ai-memory uninstall --apply --yes --mcp-url …` and removes the launchd agent. The Memory screen (F1 → "Open memory (ai-memory)", `Mode::Memory`, opened on the selected session's folder) and `agent-mux memory status|install|uninstall` share them; on the screen `/` searches the project's memory and opens a page in the Markdown viewer (`memory::query`: `ai-memory search --json`, `read-page --json`, run in the project folder since ai-memory names the project from it), `a` starts a session on a wired harness whose opening message asks the memory (`App::ask_memory`), `w` opens the web view; its input line counts as text entry and its pending steps as a confirmation (`text_entry_active`, `confirmation_active`), so local verbs leave those keys alone; steps that write a harness's settings run only on the user's `y`/`--yes`. agent-mux feeds ai-memory from its trace store (`memory::feed`): a launch whose prompts and tool calls reach the store in full (Claude with its per-launch hooks at standard/strict, Codex with agent-mux's Codex hooks; never agy) gets `AI_MEMORY_CAPTURE_OWNER=agent-mux` (`App::memory_feed_env`, a marker under `~/.agent-mux/ai-memory-feed/launches/`; loop and workflow runs are marked suppressed, not relayed), and a TUI thread relays its `hook_events` past a cursor to ai-memory's `/hook/batch` (ai-memory's hook payload shape, `extension=agent-mux`, `ingest_key` from the row key, routing and policy from `ai-memory hook --check-capture`); `App.memory_feed` is off in tests, `AGENT_MUX_MEMORY_FEED=off` turns it off. `agent-mux memory backfill` (`memory::backfill`) imports the history from before: `ai-memory backfill` in each folder the trace store has seen (not loop worktrees), planned with `--dry-run --json`; a project with captured sessions only with `--force`, and a folder once (an import stores every session again; `ai-memory-feed/backfilled`). Tests never run the real flow against the user's home: use a temporary `HOME`, `AI_MEMORY_DATA_DIR` and a server on another port (`AI_MEMORY_SERVER_URL`). Guide: `docs/memory.md`.

## Keyboard (`src/keymap.rs`, `src/app/commands.rs`)

One action registry supplies Commands, availability and shared hints. F1 opens a searchable command overlay everywhere, preserving the underlying screen and buffers; `app::shortcut_probe` records only delivered shortcuts, per app session. Focus Agents reveals and focuses the list; Return to session restores its originating session; Toggle Sidebar changes layout. F2 remains a Main-only legacy focus toggle. Tab/Shift+Tab move control focus; 1–9 select visible numbered tabs. Local verbs are n New, e Edit, d Delete, x Stop, s Save, r Run, Ctrl+R Reload, R Restore and Ctrl+O Editor; s never changes a verdict. Letters are literal in text fields; Enter inserts newlines in multiline editors, Ctrl+S saves and Esc ends field editing. The Main session pane forwards ordinary input, including plain Ctrl, Alt, Esc and Tab; never reserve those for app commands. Add actions to the registry and verify terminal delivery with `agent-mux keys`, rather than assuming modifier support means a host binding arrives. Guide: `docs/keyboard.md`; design: `docs/superpowers/specs/2026-10-11-consistent-keyboard-ux-design.md`.

## Markdown (`src/markdown/`, `src/app/markdown_view.rs`, `src/ui/markdown.rs`)

A Markdown viewer and editor: `agent-mux md <file> [--edit|--print]` (`markdown::cli`, its own terminal loop, no sessions) and `Mode::Markdown`, opened by a click on a Markdown file in the pane (`App::open_link`, `links::markdown_path_at` for plain-text paths). `markdown::render` turns a document into styled lines (pulldown-cmark) and reports links, headings and a source-line map; `markdown::mermaid` draws ```` ```mermaid ```` blocks as Unicode text (flowchart/graph, state, sequence, pie; other types show their source). `markdown::image` places an image that is a paragraph of its own and a local file (`render_with`, `Doc.images`), and the view paints it with `ratatui-image` (an SVG rasterized by `resvg` first) (kitty, iTerm2 or sixel when the environment says so, else half blocks; `$AGENT_MUX_IMAGES`); never query the terminal over stdin for it. `MarkdownView` holds the text (`TextArea`), undo, and the back stack of followed links, and answers keys with an `Outcome` its owner acts on. Guide: `docs/markdown.md`.

## Workspaces (`src/workspace/`, `src/app/workspaces_view.rs`, `src/ui/workspaces.rs`)

The Workspaces Explorer (`F1` → "Open workspaces", `Mode::Workspaces`, `ActionId::Workspaces`) and `agent-mux workspace ls|show|summarize` scan the directory tree from the launch directory (`SCAN_DEPTH = 3`, `SCAN_MAX_VISITED = 4_000`), stopping as soon as a project folder is found so internal project subdirectories are not explored, inspect each folder for its technology stack (`workspace::scan::detect_tech_stack`), git state, agent customizations (`AGENTS.md`, `CLAUDE.md`, `.agent-mux/agents/*.toml`, `.claude`, `.codex`, `.gemini`) and summary (cached LLM summary under `<library>/workspaces/<hash>.json`, manifest description, or `README.md`/`AGENTS.md` lead paragraph), and aggregate live sessions, scheduled loops and 30-day session/token/cost history both directly and rolled up across sub-folders (`workspace::activity`). In `Mode::Workspaces`, `Enter` launches a new session in the selected folder, `n` opens the New Session dialog pre-filled with that folder, `r` resumes the latest session in the folder or its sub-folders, `e` opens the folder's documentation in `Mode::Markdown`, and `s` runs a background read-only headless summary. Guide: `docs/workspaces.md`; design: `docs/superpowers/specs/2026-10-28-workspace-explorer-design.md`.

## Inter-Agent Bus (`src/bus/`, `src/mcp/server.rs`, `src/tracing/hooks/guard.rs`)

Live peer-to-peer coordination and lead-to-worker task delegation across Claude Code, Codex and Antigravity sessions sharing a workspace. Schema v16 adds `agent_messages`, `agent_tasks` and `agent_leases` to `traces.db`, woken via `<db>.wake`; the running TUI listens on a Unix domain control socket (`$AGENT_MUX_CONTROL_SOCK`, default `<snapshots>/bus.sock`, `bus::control::spawn_listener` → `AppEvent::BusControl` → `App::handle_bus_control`) for `WakeSession` (injects a prompt into an idle peer's PTY or queues it in `App::pending_bus_wakes` until the peer turns idle) and `SpawnWorker` (spawns a traced worker session in the shared workspace or an isolated git worktree under sidebar group `GroupKind::Bus` `⇄`, with `$AGENT_MUX_BUS_TASK_ID` and `$AGENT_MUX_BUS_PARENT_LAUNCH`). Both the MCP server (`agent_mux_list_peers`, `agent_mux_send_message`, `agent_mux_recv_messages`, `agent_mux_task_board`, `agent_mux_task_split`, `agent_mux_task_update`, `agent_mux_delegate`) and `agent-mux bus peers|send|recv|tasks|split|claim|done|fail|wait|delegate|lease|unlease` drive `bus::store`. `PreToolUse` (`tracing::hooks::guard::bus_lease_verdict`, `tracing::cli::hook_run`) refuses writes to files leased by another peer and injects unread `urgent` messages into `hookSpecificOutput.additionalContext`. Swarm Mission Control (`Mode::Swarm`, `src/app/swarm_view.rs`, `src/ui/swarm.rs`, model `src/bus/swarm.rs`, `agent-mux swarm status|start|broadcast|stop`; design `docs/superpowers/specs/2026-10-30-swarm-mission-control-ux-design.md`) shows one workspace's swarm as lanes (`SwarmSnapshot::lanes`: an agent and the task it holds, named `persona·harness`, never by position, with a `LaneState`) beside a panel on the selected lane (Live, Thread, Changes, Task; `a` the swarm's Activity), under a mission strip (`SwarmSnapshot::phase`); unanswered questions come from `SwarmSnapshot::open_questions` and replies carry `reply_to`; the Needs-you strip (`SwarmSnapshot::needs`, `!`, `STUCK_AFTER_NS` = 5 min, stuck from `Session::quiet_for`) lists what only the operator can resolve and retries failed or lost tasks through `bus::store::reopen_task` (a retried worktree task reuses its worktree); Activity is `SwarmSnapshot::timeline` (messages plus task and lease events); the plan gate (`swarm_plans`, schema v19, on by default) holds `SpawnWorker` and `claim_task` until the operator approves the coordinator's `plan` message (`bus::store::plan_blocks`, `decide_plan`; the prompt section is `bus::swarm::PLAN_GATE_PROMPT`); finished worktree branches are merged (`bus::swarm::merge_branch`) or set aside and recorded in `swarm_reviews`; `y` on a finished swarm (and `agent-mux swarm stop`, through `ControlRequest::StopSwarm`) stops its sessions and calls `bus::store::stop_swarm`; messages are written on the `>` command line (`swarm_view::parse_command`: `[!] [@who] [#topic] body`, `!` sends topic `urgent` so the hook delivers it mid-turn, `Tab` completes `@` names written as one word by `address_token`); its state is the `swarm_state` row (schema v17: coordinator launch, goal, `max_workers`, isolation; `bus::store::set_coordinator`/`swarm_state`/`clear_swarm`), never a bus message; a worker spawned from it runs the board task of the same id; `WakeWorkspace` wakes every live session of a workspace but the sender, which is how a broadcast with `wake` reaches the swarm; `SpawnWorker` refuses past the swarm's `max_workers` (`App::swarm_worker_cap_reached`); the screen refreshes when the bus tables' `trace_changes` triggers (schema v18), a live session or a lease expiry say so (`SwarmView::refresh_due`), never on a timer, and hands the store nanoseconds. Guide: `docs/bus.md`.

## Working in this repository

- `cargo build`, `cargo test`, `cargo clippy --all-targets`, `cargo fmt`.
- Trace store schema: `src/tracing/store/schema.rs` (migrations through `PRAGMA user_version`). Never write to a user's store from analysis code.
- Harness command lines are checked against the installed CLIs (`--help`), not documentation; record what you probed in the module docs.
